# 翻译

目录在哪里、谁来编辑、以及是什么让它们保持诚实。

## 它们落在哪里

每个源文件、每种语言一个文件，位于 `outputDir` 下——不改的话就是 `zintl/`：

```
zintl/
  src/
    App.vue.ar.json
    App.vue.fr.json
  .schemas/
    src/App.vue.schema.json
```

按源文件切分是为了编辑它们的人：打开 `Checkout.vue.fr.json` 的译者看到的是一个页面的字符串，而不是整个产品的。这与目录如何为浏览器分块无关——那件事跟随的是你的导入图，而不是你的目录树。

你的源语言没有文件。它永远不会被写出来，因为编译器已经持有这些字符串，而一份 `{"键": "键"}` 的文件不过是伪装成数据的维护负担。

## 一旁的 schema

每份目录都指向一个生成的 JSON Schema，因此支持 schema 的编辑器会给译者提供自动补全、校验，以及——在你留下 [`@zintl-note`](/reference/comment-directives) 的地方——解释这条字符串含义的注记。

它的价值比听起来更大。「Open」是动词还是形容词取决于页面，而没有上下文的译者只能猜。

## 编辑它们

就是普通 JSON。把值填上：

```json
{
  "Welcome back!": "欢迎回来！",
  "Settings": "设置"
}
```

任何留空的地方都会让构建失败。这正是它的用意。

## 当原文改动时

修改一条英文字符串，它的译文会跟着走，只要两者仍是可以辨认的同一句话。Zintl 会比较新旧文本，在足够接近时把译文带过去——`similarityThreshold` 决定「足够」的尺度，调低更宽容。

移动文件、重命名组件、重整目录：什么都不会丢。身份基于内容而非路径，所以译文附着在词句上，而不是附着在词句曾经所在的位置。

删除一条字符串，它的条目也会被移除，除非你关掉 `prune`。

## 送去别的地方

目录是 JSON，多数工具可以直接读取。当翻译系统需要 XLIFF 时，Zintl 可以导出和导入——并带上图结构对每条字符串所知的上下文，而这正是纯键值导出会丢掉的东西。

> [!NOTE]
> 导入是一道闸门，不是一次合并：回来的内容会与编译器已知的信息核对，而不是被信任并直接覆盖上去。

## 本地化资源

有些内容并不是组件里的字符串——一页正文、一张图、一份 PDF。匹配 `assetsTarget` 的文件（默认是 `.md` 和 `.txt`）是**按语言撰写**的，而不是被翻译出来的：Zintl 会在目录旁写下一个空的产物，等你把它填满。

它绝不会把原文复制过去，因为放在德语路径上的英文 PDF 并不是德语 PDF，而逐字节相同的文件是一种下游无从察觉的回退。

如果一个文件在所有语言里都一样，就不要把它列为目标。这就是「列为目标」的全部含义。
