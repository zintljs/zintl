# البداية

أربع خطوات، وآخرها اختيارية.

## التثبيت

```bash
npm install -D zintljs
```

## أضف الملحق

```ts
// vite.config.ts
import { defineConfig } from "vite";
import zintl from "zintljs/vite";

export default defineConfig({
  plugins: [zintl({ locales: ["en", "ar", "fr"] })],
});
```

أول لغة في القائمة هي لغة المصدر ما لم تحدد غيرها بـ `sourceLocale`. وهي اللغة التي تكتب بها، وهي الوحيدة التي لا يكتبها زينتل على القرص أبدًا.

تستعمل Rsbuild بدلًا من ذلك؟ الملحق وخياراته نفسها — انتبه فقط إلى عامل النشر، لأن نقطة الدخول تلك تعيد مصفوفة:

```ts
// rsbuild.config.ts
import zintl from "zintljs/rsbuild";

export default defineConfig({
  plugins: [...zintl({ locales: ["en", "ar", "fr"] })],
});
```

## عيّن اللغة

في مكان ما من نقطة الدخول، أخبر زينتل بأي لغة هذا:

```ts
// src/main.ts
import { zintl } from "zintljs/macro";

const locale = new URLSearchParams(location.search).get("lang") ?? "en";
await zintl(locale);
```

هذا الاستدعاء **مرساة ثقة**. وكل ما يمكن بلوغه منه يصير كتالوجًا واحدًا، وهو الواجهة الوحيدة من زينتل التي تلمسها معظم المشاريع.

> [!IMPORTANT]
> مرّر متغيرًا إن كان بإمكان المستخدم تغيير اللغة. `zintl("fr")` حقيقة وقت التصريف لا قيمة افتراضية: المُصرِّف يدمج الفرنسية ولا يبني البقية أصلًا، فيظهر مبدّل اللغة ويُنقر ولا يفعل شيئًا.

## شغّله

شغّل خادم التطوير واكتب نصًا عاديًا:

```ts
document.querySelector("#app").innerHTML = `<h1>Welcome back!</h1>`;
```

يستخرجه زينتل ويكتب ملفًا لكل لغة هدف داخل `zintl/`:

```json
{
  "Welcome back!": ""
}
```

املأ القيم الفارغة. هذا هو سير العمل كله — الجانب الإنجليزي لا يُكتب أبدًا، لأن المُصرِّف يملكه أساسًا.

## ماذا يحدث إن نسيت واحدة

يفشل بناؤك، ويسمّي النص واللغة.

هذا مقصود، وهو الشيء الوحيد الذي ينبغي فهمه قبل المضي: زينتل لا يملك أي رجوع إلى لغة المصدر، فلا يمكن لترجمة ناقصة أن تصل إلى مستخدم متنكرة في هيئة نص إنجليزي. وإن كنت تفضّل رؤية الفشل في المتصفح بدلًا من CI، فـ `verifyIntegrity` هو ما يتحكم بذلك — لكن الإعداد الافتراضي هو الذي يلتقطه أبكر.
