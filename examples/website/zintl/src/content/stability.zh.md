# 稳定性

Zintl 处于 alpha 阶段。本页说明这在实践中意味着什么，好让你判断可以依赖哪些部分。

## 已经定下来的

以下都有契约测试作后盾，预计形态不会再变：

- **宏本身。** `zintl(locale)`，以及传变量与传字面量之间的区别。
- **不回退到源语言。** 缺失的翻译是构建错误。这是设计，不是默认值。
- **基于内容的身份。** 移动或重命名文件不会让它的译文变成孤儿。
- **目录格式。** 每个源文件、每种语言一个 JSON 文件，旁边配一份 schema。
- **与分块对齐的目录。** 译文沿你的导入图切分。
- **幽灵模式。** 源语言永远不会被写入磁盘。

## 仍在变动的

- **选项名。** 有些比需要的更具体，可能会在给出弃用提示后改名。
- **切面的编写。** 编写自定义切面的内部契约尚未冻结。使用内置切面是安全的；针对当前接口写一个则可能需要调整。
- **SSR 与流式渲染。** 在 Vite 上受支持，也被测试套件覆盖，接口面仍可能继续扩展。
- **vinext。** 实验性，含义是它没有端到端覆盖。

## 不在计划中的

- **运行时的 `t()` API。** 如果你需要在运行时按键查找字符串，那 Zintl 的形态就不对。
- **自动机器翻译。** 目录就是文件；你想用什么跑一遍都行。
- **回退链。** 见第一份清单。

## 版本

alpha 版本带有版本后缀和相应的 npm dist-tag。只要主版本号还是 `0`，破坏性变更就随次版本发布，且每一项都附带一份 changeset，说明改了什么、为什么改。

## 移除 Zintl

这值得在采用之前就知道，而且它本就设计得很短：

1. 从打包器配置里删掉插件。
2. 你的源码没有变化——它一直都是普通字符串。它会继续以你的源语言正常工作。
3. 如果你不想留着译文，删掉 `outputDir`。

没有 eject 步骤，仓库里也没有需要拆解的生成代码，因为 Zintl 从不往你的源码里写东西。这是任何你允许靠近自己代码库的东西都值得要求的一条性质，也正是本页可以如此简短的原因。

## 反馈问题

任何令人意外、不清楚或明显有毛病的地方，都值得开一个 [issue](https://github.com/zintljs/zintl/issues)。真实使用中的反馈，眼下比其他任何东西都更有分量——包括「我没弄明白该怎么……」，那是一个文档缺陷，也会被当作缺陷来处理。
