# 复数与语法

英语有两种复数形式。阿拉伯语有六种。你的源码不该需要知道这件事。

## 问题，只说一次

```ts
const label = `${count} items`;
```

这在多数语言里都是错的，而常见的补救只会让源码更糟：一个只覆盖两种情况的三元表达式，或者一次带 `count` 参数的 `t()` 调用，外加一个你现在还得起名的键。

## Zintl 的做法

你写句子。译者在目录里用 ICU 语法写语法规则：

```json
{
  "{count} items": "{count, plural, other {# 个条目}}"
}
```

你的源码始终写着 `${count} items`。阿拉伯语目录带六种形式，因为阿拉伯语有六种；中文一种也不带，因为中文不需要。语法的复杂度，留在语法所在的地方。

## 而且它会被编译掉

那段 ICU 字符串不会在浏览器里解析。在编译期，它会变成一个普通的 JavaScript 函数：

```js
(params) => {
  const { count } = params;
  return `${count} 个条目`;
};
```

没有任何消息格式化库会抵达你的用户。为了处理一条编译期就已知的规则，却把语法引擎发给每一位访客——这正是本项目要去掉的那种重量。

## 在两种措辞之间选择

`select` 的工作方式相同，适用于任何不是计数的场合：

```json
{
  "Invite them": "{gender, select, male {邀请他} female {邀请她} other {邀请对方}}"
}
```

## 当原文里根本没有那个词

有些语言需要知道你的英文句子从未提及的性别。与其为了给译者一个着力点而扭曲英文，不如把这个值悄悄传过去：

```ts
// @zintl-pass gender={user.gender}
const invite = `Invite them`;
```

源码读起来和原来一模一样。`gender` 会出现在生成的 schema 里，译者可以据此分支。

> [!NOTE]
> 这是一个逃生出口，用来应对「目标语言往往需要比原文更多的上下文」这一事实。没有它，通常的变通办法就是把英文写差一点，去迁就一门它本来就不是用来书写的语言。
