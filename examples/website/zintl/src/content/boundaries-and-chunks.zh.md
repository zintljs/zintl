# 边界与分块

Zintl 把翻译当作打包问题来处理。下面的一切都由此推导而来。

## 流水线

```
你的代码 ──▶ 提取器 ──▶ 编译器 ──▶ 插件 + 运行时
             (有什么)   (什么该    (浏览器实际
                         放一起)     加载什么)
```

**提取器**用解析器读取你的源码并报告它找到的内容。它从不修改文件，也不携带任何框架知识——React、Vue 与 Svelte 的行为都是以配置的形式抵达的。

**编译器**决定什么该放在一起：它构建边界图、把目录切成分块、编译语法规则，并在字符串变动时让译文继续附着其上。

**插件与运行时**把这一切接到你的构建工具和浏览器上。

## 锚点与边界

一次 `zintl(locale)` 调用就是一个**信任锚点**——你的应用在此决定自己处于哪种语言。

从每个锚点出发，Zintl 遍历可达的导入，收集所有可能出现的字符串。这个集合就是一个**边界**，而一个边界会成为一个目录分块。

```
src/main.ts        zintl(locale) ──┐
  └─ Header.tsx                    ├──▶ 一个边界，一个分块
     └─ Nav.tsx                  ──┘

src/admin.ts       zintl(locale) ──┐
  └─ Charts.tsx                    ├──▶ 另一个边界
                                 ──┘
```

每个锚点都是独立的。嵌套在函数内部的 `zintl()` 调用是它自己的边界，有自己的加载生命周期——它刻意不从上层继承任何东西，因此加载什么是可预期的，而不是碰巧发生的。

回报是：打开你设置页的人下载的是设置页的翻译。不是全部。

## 为什么不用一本大字典

常见做法是把所有字符串放进一个对象，一次性加载。它很简单，代价是读你落地页的人会下载他永远看不到的页面的译文。这份代价随应用增长，而且在它变大之前一直是隐形的。

沿着打包器本来就在用的边界去切分翻译，让两者保持一致：懒加载路由的译文，随那个路由一同到达。

## 身份基于内容

一个边界由其内容的哈希标识，而不是由它来自哪个路径。移动文件，边界还是同一个边界。

这正是重构不会让你事后花一天去核对目录的原因，也是代码库给自己立的约束：任何把翻译身份绑到文件路径或行号上的做法，都是倒退。

## 提取是结构化的

Zintl 提取的不是裸字符串，而是**意义单元**。模板字面量、JSX 片段与 HTML 会先被缝合成逻辑片段，于是：

- 被标签拆开的句子仍然是一个可翻译的句子，
- 插值会变成稳定的占位符，而不是按位置编号的噪声，
- 同一个片段无论出现在哪里都产生同一个键。

最后一点正是译文能挺过重构的原因。本站自己的标题就是一个包含两个 `<span>` 的键，因为它本来就是一句话。

## 切面

框架支持、SSR、资源处理与打包器集成，都是彼此独立、可组合的部件，称为**切面**，在构造编译器时解析，而不是以条件分支散落其中。

添加一个框架或一种构建工具，意味着贡献一个切面，而不是改动内核。两个切面争夺同一个扩展名是硬错误，而不是悄无声息的「后者胜出」。

Rsbuild 就是这一主张的检验。它运行在 Rspack 上，其插件模型与 Rollup 的差异之大在打包器之间已属极限，而它达成对等时，编译器里没有一处 Rspack 专用分支。
