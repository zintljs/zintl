# 集成

Zintl 需要在掌管你分块图的那个打包器里占一个插件席位。这份清单完全由这一点决定。

## 它在哪里可用

| 宿主                       | 框架                                         | 应用形态                        | 状态   |
| :------------------------- | :------------------------------------------- | :------------------------------ | :----- |
| **Vite** 6 / 7 / 8         | React、Preact、Solid、Vue、Svelte、Lit、原生 | 单页、多页、SSR、按语言静态构建 | 已支持 |
| **Rsbuild** 2.x            | React、Preact、Solid、Vue、Svelte、Lit、原生 | 单页、多页                      | 已支持 |
| **经由 vinext 的 Next.js** | React（App Router、RSC）                     | SSR                             | 实验性 |

除最后一行外，每一行都由契约测试套件端到端驱动：每次改动都用真实浏览器跑真实应用。

## Vite

参考实现。本文档中的一切都无保留地适用。

## Rsbuild

与分块对齐的目录——包括 `await import()` 之后的路由——幽灵模式、本地化资源、`<html>` 上按语言设置的 `lang` 与 `dir`，以及开发期的字符串编辑，全部原样适用，编译器里没有任何 Rspack 专用代码。

有两件事仅限 Vite，而且属于尚未构建，而非被阻断：

- **`multiplex`**——按语言展开 HTML。
- **SSR。**

尚未构建它们的打包器会通过自己的切面声明这一点，因此把两者组合起来会大声失败，而不是悄悄失败。

Rsbuild 能跑起来这件事本身，就是切面架构的证据。Rspack 的插件模型与 Rollup 的差异之大在打包器之间已属极限，而达成对等并不需要在编译器里加分支——只需要第二个打包器切面。

## 经由 vinext 的 Next.js

实验性。在 Vite 之上运行的 React，配合 App Router 与 RSC。

## 什么不受支持，以及为什么

**运行在 webpack 或 Turbopack 上的 Next.js。** Turbopack 没有公开的插件 API，而我们也不打算在 Next.js 正在远离的那个打包器上构建。`vinext` 是受支持的路径，且是实验性的。如果你今天需要在标准 Next.js 上做 i18n，Zintl 不是那个工具。

**Nuxt、SvelteKit、Astro、Remix、TanStack Start。** 它们跑在 Vite 上，所以插件*会*加载，看起来也像能用。但这些都没有经过测试，它们的路由与 SSR 入口形态也没有被建模。请把它们当作尚未探索，而不是当作可用。

**webpack、Rollup、esbuild、Farm。** 没有任何打包器切面认领这些宿主，因此插件会拒绝构建，而不是产出某种细微错误的东西。

> [!NOTE]
> 如果你撞上了其中之一，[请开一个 issue 说出来](https://github.com/zintljs/zintl/issues)。下一个该支持哪个宿主，我们更愿意依据反馈来决定，而不是靠猜。

## 自己加一个

提取器不携带任何框架知识，编译器与打包器无关。两者都由**切面**组合而成，所以支持另一个框架或另一种构建工具，是你去添加的东西，而不是需要围绕它重写内核的东西。
